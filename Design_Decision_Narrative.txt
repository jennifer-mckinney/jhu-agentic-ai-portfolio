CAPSTONE: SENIOR MORTGAGE UNDERWRITING SYSTEM
ADVANCED AGENTIC AI PROGRAM
JHU Agentic AI Portfolio — Design Decision Narrative

================================================================================
INTRODUCTION
================================================================================

This document traces the key design decisions and architectural improvements
made during the development of the Senior Mortgage Underwriting System, a
multi-agent AI application for mortgage loan underwriting. Each decision point
reflects deliberate engineering choices driven by regulatory compliance
requirements, software architecture best practices, and a commitment to
building production-grade AI systems rather than mere academic prototypes.

The principle that unifies all nine decisions is simple:
  IN REGULATED AI, THE ARCHITECTURE IS THE COMPLIANCE FRAMEWORK.

(diagram in conclusion)

================================================================================
DECISION 1: REGULATORY FRAMEWORK AS ARCHITECTURE DRIVER
================================================================================

Context:
The course template provided basic agent skeletons. Jennifer recognized that
mortgage underwriting is one of the most heavily regulated domains in financial
services.

Decision:
Embed regulatory compliance (ECOA/Reg B, Fair Housing Act, Dodd-Frank ATR/QM,
NIST AI RMF, Colorado SB 24-205) directly into agent system prompts rather than
treating compliance as an afterthought.

Impact:
Every agent decision is traceable to specific regulatory requirements. The
system produces audit-ready output that meets SR 11-7 model risk management
standards. This transforms the project from a coding exercise into a deployable
compliance framework.

================================================================================
DECISION 2: PII REDACTION — ARCHITECTURE DEFENSE IN DEPTH
================================================================================

Context:
The template included a basic sanitization function with placeholder fields.

Decision:
Implement source-level PII redaction that sanitizes data before it reaches any
LLM, following GLBA (Gramm-Leach-Bliley Act) financial privacy requirements.
SSN masked to last 4 digits, names replaced with [APPLICANT_NAME], addresses
redacted, phone numbers masked.

Impact:
Data protection happens at the system boundary, not at the display layer. This
is a fundamental architectural principle — sensitive data never enters the AI
processing pipeline. Compliant with GDPR, CCPA, and GLBA simultaneously.

NOTE FOR PATENT: This is the PII Non-Acquisition Pattern (PNAP) as implemented
in the financial/mortgage domain. Structural exclusion at system boundary —
identical architectural principle to srs-ai-assist pharma implementation.

================================================================================
DECISION 3: BIAS DETECTION BEYOND THE TEMPLATE
================================================================================

Context:
The template provided a basic bias check function with minimal protected terms.

Decision:
Expand the protected characteristics list to cover all federally protected
classes (race, color, religion, national origin, sex, marital status, age,
gender, disability, familial status) AND add proxy discrimination detection for
zip code-based redlining patterns.

Impact:
The bias detection system catches both explicit discrimination and subtle proxy
discrimination. This reflects real-world fair lending examination standards used
by the CFPB and OCC. The system flags potential disparate impact before
decisions are finalized.

NOTE FOR PATENT: This is the Bias-Triggered Regression Feedback Loop (BTRFL)
as implemented in the mortgage domain. bias_flags > 0 triggers mandatory
escalation — same pattern as finance/pharma BTRFL override logic.

================================================================================
DECISION 4: DTI AS SYSTEM OF RECORD
================================================================================

Context:
During testing, the TC2 Final Report displayed a DTI of 113.47%. Investigation
revealed the execution cell's sum(debts.values()) was double counting because
the JSON included both individual debt items AND a total_monthly_debt field.

Decision:
Rather than patching the calculation at the display layer, established the
principle that execution cells are the system of record. Final Reports and HITL
cells consume exported values — they never recalculate. The known DTI bug in
the course template was documented but not "fixed" at the presentation layer to
avoid introducing inconsistency.

Impact:
This enforced a clean separation of concerns: computation happens once, at the
source, and all downstream consumers reference the same canonical values. This
is a core principle in financial systems — a single source of truth prevents
reconciliation errors.

================================================================================
DECISION 5: HITL ESCALATION — RISK-BASED THRESHOLDS
================================================================================

Context:
The project required human-in-the-loop review capability but didn't specify
escalation criteria.

Decision:
Implement a three-trigger escalation framework:
  (1) risk_score >= 65        — elevated risk
  (2) bias_flags > 0          — any discrimination concern
  (3) decision == "DENIED"    — adverse action requires human review

The HITL interface uses a split-pane layout with system analysis on the left
and human decision controls on the right.

Impact:
Escalation is deterministic and auditable. Every denied application gets human
review (Fair Housing compliance). Any bias concern triggers immediate escalation
regardless of risk score. This maps directly to CFPB examination procedures for
fair lending oversight.

NOTE FOR PATENT: This is the CGAL (Confidence-Gated Autonomy Loop) regulatory
override trigger as implemented in the mortgage domain. risk_score >= 65,
bias_flags > 0, decision == DENIED are the domain-specific override conditions
— identical architectural pattern to pharma/finance CGAL override logic.

================================================================================
DECISION 6: AGENT PROMPTS AS REGULATORY INSTRUMENTS
================================================================================

Context:
Each specialist agent (Credit, Income, Asset, Collateral, Critic, Decision)
needed system prompts.

Decision:
Design each agent's system prompt as a regulatory compliance instrument that
specifies:
  (a) applicable regulations
  (b) required analysis framework
  (c) structured output format for audit trails
  (d) explicit instructions to avoid protected characteristic references

Impact:
Agent outputs are structured for regulatory examination. Each analysis follows
a consistent framework that maps to agency examination procedures. The Critic
agent specifically cross-validates all analyses for consistency and compliance
before the Decision agent renders judgment.

================================================================================
DECISION 7: RAG-ENHANCED POLICY RETRIEVAL
================================================================================

Context:
The template included a placeholder for policy document loading.

Decision:
Implement full RAG pipeline using:
  - PyPDFLoader for policy document ingestion
  - RecursiveCharacterTextSplitter with 1000-token chunks, 200-token overlap
  - ChromaDB vector store for semantic policy retrieval

Impact:
Agents can retrieve specific underwriting policies relevant to each application
rather than relying on static rules. This enables the system to adapt to policy
changes without code modifications — a key requirement for production mortgage
systems where guidelines update quarterly.

================================================================================
DECISION 8: THREE PROFILE TEST STRATEGY
================================================================================

Context:
The project required test cases to validate the system.

Decision:
Design three test profiles that span the full decision spectrum:
  (1) Strong Applicant    — 760 credit, 30.4% DTI, W2 employed → APPROVED
  (2) Borderline Applicant — 680 credit, 42% DTI, employment gap → CONDITIONAL
  (3) Weak Applicant      — 595 credit, 50% DTI, bankruptcy, collections → REJECTED

Impact:
Each profile tests different decision paths and risk factor combinations. The
borderline case is particularly valuable — it forces the system to demonstrate
nuanced conditional approval logic with specific stipulations rather than
binary approve/deny. This mirrors real underwriting where most applications
require conditions.

================================================================================
DECISION 9: QUALITY OVER SHORTCUTS — ROOT CAUSE RESOLUTION
================================================================================

Context:
Throughout development, multiple bugs and inconsistencies were discovered (DTI
double-counting, display formatting issues, export variable mismatches).

Decision:
For every issue, trace to root cause rather than applying display-layer patches.
When root causes were in course-provided template code, document the issue and
maintain consistency rather than introducing divergent calculations.

Impact:
The codebase maintains internal consistency. Every number displayed can be
traced to its source — in a production system, this discipline is what separates
academic prototypes from production-grade financial software.

================================================================================
CONCLUSION
================================================================================

These nine decisions collectively transform a course template into a system
that reflects production mortgage underwriting standards. The common thread is
treating regulatory compliance, data integrity, and architectural discipline not
as constraints but as design drivers.

In regulated AI, the architecture IS the compliance framework, and every design
choice either strengthens or undermines the system's fitness for purpose. This
project demonstrates that agentic AI systems in financial services require the
same rigor as the human processes they augment — clear accountability, traceable
reasoning, and unwavering commitment to fairness and accuracy.
